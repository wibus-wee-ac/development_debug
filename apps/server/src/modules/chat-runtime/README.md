# Chat Runtime Module

Provides server-owned chat turn execution for existing sessions, including text/file user input, durable continuation queue items, AI SDK `UIMessageChunk` SSE streaming, final `UIMessage` snapshot persistence through AI SDK stream finish callbacks, usage writes, run state updates, cancellation terminal transitions, and ACP live runtime orchestration.
`messages.message_json` is the only hydration source of truth. Stored message snapshots are Cradle-internal trusted `UIMessage` JSON; this module parses them directly instead of running a second Zod projection schema over AI SDK-owned message state.
Provider turn context is intentionally reconstructed through a Cradle-owned transcript layer: ordinary new turns read recent complete top-level messages from `messages.message_json`, preserve the stored `UIMessage.parts` structure, and expose a bounded `CradleTurnTranscript` for provider-specific native history projectors. Native approval continuation still uses the explicit AI SDK `messages` request body because it must preserve tool lifecycle state exactly as supplied by the client. Final assistant snapshots are projected incrementally while chunks are published, so terminal finalization does not replay the active run buffer through AI SDK stream reconstruction. Final snapshots and oversized historical snapshots are compacted with server-owned limits so old tool/reasoning payloads do not create unbounded parse, stringify, replay, or response costs.
`POST /chat/sessions/:sessionId/response` accepts ordinary text/file input, chat-owned `contextParts`, and AI SDK `messages` history. The `messages` form is used for native tool approval continuation: the last assistant `UIMessage` already contains the `approval-responded` tool part, and the server reuses that assistant message id so AI SDK can continue the same tool lifecycle through `convertToModelMessages` and `collectToolApprovals`.
Passive observers hydrate through `GET /chat/sessions/:sessionId/messages`, then join the currently active run through `GET /chat/sessions/:sessionId/stream`; the session stream replays a coalesced active-run AI SDK chunk buffer before live chunks so late Workspace Detail joins rebuild the active assistant message through AI SDK protocol consumption without retaining every high-frequency text/reasoning/tool delta.
Codex active-goal continuation is a Chat Runtime run-lifecycle concern. When a Codex run ends without user cancellation while the provider snapshot still contains an active goal, Chat Runtime schedules a deduped follow-up system run after the Codex-native continuation delay, creates a new assistant message for that run, and sends an internal metadata-marked user message to the provider without inserting a visible user message. User cancellation and queued user turns take precedence: cancellation pauses the provider-owned goal through Codex before aborting, and pending queue rows drain before any automatic goal continuation. `/chat/sessions/:sessionId/runtime-status` exposes `hasActiveGoal` so passive renderers can keep polling long enough to discover the new active run and join its session stream.
`GET /chat/sessions/:sessionId/capabilities` owns the session-scoped runtime capability inventory returned to the renderer. Its payload now includes runtime-native slash commands, provider-projected UI slots, and skill ids, so composer presentation can stay provider-driven instead of hard-coded in the frontend.
`GET /chat/sessions/:sessionId/ui-slot-states` returns provider-owned state for declared UI slots. Renderer surfaces are selected from `RuntimeUiSlot.surfaces`: `composerState` can render primary workflow state near the composer, `slashCommand` can enter the slash panel, `toolbarPicker` can expose option summaries next to existing toolbar controls, `runtimePanel` can render Right Aside Runtime summaries, and `streamEvidence` is consumed by message/tool blocks from provider-emitted chunks. Polled slot state is a current snapshot and must not be used to synthesize transcript-positioned message-bubble content. Codex `goal` is read from the app-server thread goal object; Codex `compact` separates context-compaction item lifecycle from thread token-usage meter state, using `contextCompaction` item start/complete as the primary lifecycle source and deprecated `thread/compacted` only as a compatibility signal; Codex `status`, `model`, and `reasoning` are projected from thread start/resume responses, settings/status notifications, config, model list, and model-provider capability reads. Codex `plan`, `toolActivity`, `mcp`, `diff`, `terminal`, `approvals`, `alerts`, `filesystem`, `search`, and `usage` are projected from their app-server notifications and bounded provider snapshots; `skills`, `plugin`, `crew`, and `config` use provider list/read methods at render time. Chat Runtime stores only the provider snapshot needed to replay those projections; it does not own goal, compaction, plan, tool, MCP, model, reasoning, diff, terminal, approval, alert, filesystem, search, usage, skill, plugin, crew, or config lifecycle semantics.
User attachments are represented as AI SDK `FileUIPart` entries in `UIMessage.parts`; the OpenAI-compatible AI SDK provider converts those through `convertToModelMessages`, Codex maps image parts into app-server `UserInput` items, and text-only runtime providers reject unsupported parts explicitly instead of silently dropping attachments. Chat-owned context parts such as `data-cradle-skill` are persisted in the same snapshots but projected only by providers that support them.
`POST /chat/sessions/:sessionId/cancel` owns the canonical aborted transition: it marks active runs/messages terminal before asking the provider to stop, ignores late provider chunks after terminal state, and repairs persisted `streaming` rows when no in-memory active run exists. `POST /chat/sessions/:sessionId/permission-mode` forwards active-run `bypassPermissions` / `plan` switches only to providers that own a live permission side-channel. `GET /chat/sessions/:sessionId/messages` also repairs orphaned persisted `streaming` rows when there is no active or pending in-memory run, so reload recovery does not expose stale in-progress state after a process exit.
Runtime skill path discovery is cached per workspace for a short window so simultaneous chat turns do not repeatedly perform synchronous directory scans during provider startup. Providers still receive Cradle-owned skill paths only as read inputs; skill lifecycle stays under the skills namespace.
Provider-native session titles are projected through the `StreamTurnInput.reportSessionTitle` callback. Chat Runtime owns the write into `sessions.title`; providers only report titles they read from their own runtime/session metadata.
Route metadata includes `x-cradle-cli` descriptors for non-streaming generated CLI commands.
Chat stream traces are opt-in through `CRADLE_CHAT_STREAM_TRACE=1` and are written to `CRADLE_DATA_DIR/chat-runtime/traces/*.jsonl` with bounded payloads by default. Use `CRADLE_CHAT_STREAM_TRACE_FULL=1` only for short diagnostic runs because full provider raw events, mapper output, runtime chunks, and emitted AI SDK SSE frames can be very large.
Lightweight runtime profiling is opt-in through `CRADLE_CHAT_RUNTIME_PROFILE=1`; it logs per-run stream/finalize timings, final snapshot bytes, replay chunk count, output diagnostics, and process memory deltas without writing extra trace files.
Chat Session queue and steer are owned here: `/chat/sessions/:sessionId/queue` stores follow-up turns in `chat_session_queue_items`, including per-item permission mode and selected context parts for compatible runtimes, applies true live steering only when the active provider exposes the optional `steerTurn` hook, persists visible continuation messages with `metadata.cradle.continuation`, otherwise drains `steer` items before normal `queue` items after the active run completes, and does not write into Issue Agent namespaces.
Codex app-server bridge routes are owned here because they are session-scoped Chat Runtime capabilities. `/chat/sessions/:sessionId/codex/app-server/capabilities` exposes the generated app-server method/request/notification surface, `/invoke` performs one-shot JSON-RPC calls, and `/stream` keeps the app-server connection open while forwarding raw notifications and handled server requests as SSE events. `/invoke` synchronizes `thread/goal/set` and `thread/goal/clear` results into the Cradle backend-session binding snapshot so composer goal controls, runtime status polling, and automatic continuation scheduling observe the same provider-owned goal state. The bridge reads Codex profile/session config and writes only Cradle backend-session binding state; Codex protocol semantics and tool envelope mapping stay in `../chat-runtime-providers/codex`.
Provider tool envelope shape is owned by `../chat-runtime-providers/tools`, while provider-specific tool identity and payload semantics live in each provider directory such as `../chat-runtime-providers/claude-agent/tools` and `../chat-runtime-providers/codex/tools`. Provider adapters emit tool input/output payloads as `{ identifier, apiName, args, result }` envelopes while Chat Runtime only persists and streams the AI SDK chunks. Claude Agent `TodoWrite` state is carried inside the Claude Code tool result envelope as `result.pluginState.todos`, and the existing terminal tool message snapshot persistence writes that state into `messages.message_json`.

## Files

- `index.ts`: Elysia route surface for `POST /chat/sessions/:sessionId/response`, `GET /chat/sessions/:sessionId/stream`, queue routes, runtime capability/UI-slot-state/status routes, Codex app-server capabilities/invoke/stream routes, message snapshot routes, trace routes, permission mode, and cancellation.
- `model.ts`: HTTP params/body schemas for the chat runtime surface, including optional text plus AI SDK file parts, chat-owned context parts, optional AI SDK `messages` history for approval continuation, optional `providerTargetId` overrides for response/queue/Codex app-server requests, queued and active permission mode requests, server-owned runtime status responses, Codex app-server bridge responses, and decoded chat stream trace responses.
- `service.ts`: active-run orchestration, runtime-native capabilities discovery, Codex app-server bridge context resolution, duplicate-run reservation, provider target override resolution with runtime/provider compatibility validation, provider target + agent + session runtime config merging, Chronicle long-term memory context injection, text/file draft `UIMessage` persistence, provider-native session title projection into `sessions.title`, AI SDK assistant-message continuation for native approval responses, durable queue item list/enqueue/cancel/reorder/drain, continuation metadata persistence for visible steer/queue messages, Codex active-goal system-run continuation scheduling, direct AI SDK `UIMessageChunk` SSE publication, incremental final `UIMessage` projection, trusted snapshot hydration with orphaned streaming repair, session-level passive stream subscription with coalesced active-run replay, server-owned runtime session status projection, cancellation terminal-state ownership, persisted streaming cleanup, completion subscription, trace retrieval, and event broadcasting.
- `message-snapshots.ts`: trusted internal `UIMessage` helpers for stored snapshot parsing, assistant/user message construction with text, context, and file parts, Codex internal goal-continuation metadata, and text extraction. This file intentionally avoids Cradle-owned Zod schemas over AI SDK message internals.
- `context-parts.ts`: Chat Runtime-owned structured context part helpers for validating and projecting Cradle-owned `data-cradle-*` message parts such as selected Skills.
- `transcript.ts`: Cradle-owned transcript reconstruction from stored `messages.message_json`, including bounded history selection, invalid-snapshot fallback, and structural `UIMessage` preservation for provider projectors.
- `stream-trace.ts`: dev-mode JSONL trace writer/reader for the provider raw event, mapper output, runtime chunk, SSE emit, and run terminal chain.
- `ui-message-input.ts`: provider-boundary helpers for extracting text from `UIMessage` and rejecting attachments for text-only runtimes.
- `chat-turn-context.ts`: system prompt and history resolution.
- `chat-runtime-provider-registry.ts`: runtime provider registry for ACP Chat, OpenAI-compatible, Claude Agent, Codex, System Agent (`jar-core`), and debug/mock variants. It registers adapters from `../chat-runtime-providers` and keeps cached runtime skill path discovery under Chat Runtime because skills are resolved per chat workspace.
- `runtime-provider-types.ts`: chat runtime provider contracts, including UI slot surfaces, provider-owned UI slot state unions for goal, compact usage and lifecycle, plan, tool activity, MCP, model, reasoning, status, diff, terminal, approvals, alerts, filesystem, skills, plugin, search, crew, usage, and config; the optional `steerTurn` side-channel used only by providers that can inject input into an active turn; and the `reportSessionTitle` callback for provider-native title projection.

`../chat-runtime-engine` owns provider-agnostic AI SDK execution helpers, compaction, and provider selection. `../chat-runtime-providers` owns concrete backend adapters. Chat Runtime depends on both through narrow contracts and keeps HTTP routes, persistence, queueing, trace files, and run lifecycle semantics here.

## Provider MCP Ownership

The server MCP registry owns MCP server discovery for both plugin-registered servers and host-owned builtin servers such as Chronicle. Chat runtime providers in `../chat-runtime-providers` only read that registry when their upstream runtime supports MCP-style tool servers:

- Claude Agent receives the registry through SDK `mcpServers` query options.
- ACP receives the registry on `newSession`, `loadSession`, and `unstable_resumeSession` as ACP `McpServer[]`.
- Codex receives the registry through `config.mcp_servers`.

OpenAI-compatible and System Agent (`jar-core`) providers do not currently expose a compatible plugin-MCP injection surface in this module.

## Live Steer Ownership

`ChatRuntime.steerTurn` is optional. Chat Runtime first persists every follow-up as a `chat_session_queue_items` row, then tries live steering only for active providers that expose this hook. Before calling the provider, the service atomically claims the row from `pending` to `running` and links it to the active run through `startedRunId`, so cancel/reorder/drain cannot race the provider side effect. If the provider accepts the steer message, the queue row is marked `completed` and a completed user message is inserted into Chat Session history with `metadata.cradle.continuation.mode = "steer"` for renderer presentation. If history persistence fails after provider acceptance, the row remains `completed` with `errorText` so the already-applied input is not replayed. If the provider rejects live steering or does not implement the hook, the row stays or returns to `pending` and the normal queue drain starts it as a later turn. This keeps the HTTP and database contract durable while avoiding fake live steering for runtimes that cannot support it.

Claude Agent supports this hook through the Claude Agent SDK streaming-input query plus `interrupt()`. Codex supports this hook through the Codex app-server JSON-RPC protocol: the provider keeps the active app-server client, `threadId`, and `turnId`, then sends `turn/steer` with the expected active turn id. ACP, OpenAI-compatible, System Agent, and mock runtimes currently fall back to durable queued steering unless their providers add a real side-channel later.

Chronicle registers a builtin `chronicle` MCP server from `../chronicle/mcp.ts`, exposing read-oriented memory, activity segment, and knowledge-card tools to the providers above. Chat Runtime remains a consumer of that registry and does not own Chronicle semantics or writes.

## Chronicle Context

Chat runtime reads Chronicle-owned memory context through `../chronicle/agent-context.ts` during turn context resolution. It uses the current user message as a keyword query, injects a small read-only `Chronicle long-term memory context` block into the system prompt when relevant memory or knowledge exists, and redacts common sensitive values before the prompt reaches the selected runtime provider. The helper intentionally avoids importing the main Chronicle service so chat execution does not create a Chronicle-to-chat dependency cycle or trigger local embedding health probes during ordinary turns.

## ACP Client Filesystem Ownership

ACP `fs.writeTextFile` writes to the client filesystem, not to Cradle-owned data. The legacy Cradle approval SSE owner has been removed from chat runtime, so `../chat-runtime-providers/acp/connection-manager.ts` must fail closed and leave the target file unchanged until ACP filesystem writes are represented as AI SDK tools with native `needsApproval`. Do not reintroduce a separate approval stream or wrapper for this path.

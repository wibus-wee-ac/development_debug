# Codex Runtime Provider

Owns the Codex app-server runtime adapter for Chat Runtime. This directory translates between Cradle `UIMessage` state and the Codex JSON-RPC app-server protocol.
Codex tool identity and the `{ identifier, apiName, args, result }` envelope are owned by `tools/`; this provider only maps app-server protocol items into that stable contract.
Selected chat Skills arrive as Cradle-owned `data-cradle-skill` message parts. The provider reads them and projects them into Codex app-server `UserInput` skill items without writing to any skills namespace.
Codex thread names are read from app-server `thread/start`/`thread/resume` responses and `thread/name/updated` notifications, then reported through Chat Runtime's title callback. Cradle owns the final `sessions.title` write.
Codex app-server child processes receive Cradle-owned `CRADLE_CHAT_SESSION_ID` and, for workspace-bound sessions, `CRADLE_WORKSPACE_ID` as environment hints so tools and shell subprocesses can call back into Cradle with the current chat/workspace context. These values are convenience context only; authoritative ownership still comes from Chat Runtime resolving `sessions.workspaceId`.
Existing Codex threads are resumed with `excludeTurns: true`, then immediately read through `thread/turns/list` using `itemsView: "full"` and ascending pagination. Cradle stores that best-effort full app-server turn page in the provider snapshot under the Codex namespace it owns; this captures everything app-server can reconstruct from persisted Codex rollout history without writing duplicate native history back into Codex. When a later provider-target change forces a fresh Codex thread, Cradle carries the previous Codex native history snapshot through `StartChatSessionInput.previousProviderStateSnapshot`, projects it to Responses API items, and injects it before the first turn so the new thread receives the richest app-server history Cradle had already fetched.
Goal slash commands and internal goal continuations are provider-native control messages, not chat text. A visible `/goal` command or goal metadata message sets `thread/goal/set` with an objective, and an internal Chat Runtime goal-continuation message sets `thread/goal/set` with `status: "active"` without calling `turn/start`. The provider then streams the resulting app-server notifications as the current run. User cancellation pauses an active Codex goal in the provider snapshot before interrupting the current turn so Chat Runtime does not auto-resume from stale active-goal state.
Codex app-server stream failures keep user-facing errors short: retry-limit and status failures are summarized through `CodexProviderError.data.details`, while full raw event samples, counts, and app-server error notifications stay in `data.diagnostics` for observability/debugging.
Codex token usage notifications stay provider-owned at the protocol boundary: `thread/tokenUsage/updated` is projected into Codex UI slot state and the provider's `lastUsage` / `lastModelId` read model. Chat Runtime owns the durable `usage_logs` write during run finalization.
Codex UI slots are projected from the app-server capability manifest and declare their intended Cradle surfaces. Slot state stays provider-owned: `goal` reads `thread/goal/get` and can render in composer state plus slash/runtime surfaces; `compact` starts from the provider-native `thread/compact/start` request instead of a raw `turn/start` slash message, keeps lifecycle from `contextCompaction` item `item/started` and `item/completed`, treats deprecated `thread/compacted` only as a compatibility signal, and keeps the usage meter from thread-level `thread/tokenUsage/updated` plus effective config limits such as `model_auto_compact_token_limit`; `status`, `model`, and `reasoning` come from thread start/resume responses, settings/status notifications, config, model list, and model-provider capability reads; `plan` uses `turn/plan/updated` as the canonical session plan snapshot; `toolActivity` summarizes recent `item/started` and `item/completed` lifecycle records; `mcp` merges `mcpServerStatus/list` reads with startup, OAuth, and progress notifications; `diff`, `terminal`, `approvals`, and `alerts` summarize their corresponding app-server notifications without storing full output history, with `alerts` exposed only as runtime-panel snapshot state; `filesystem`, `search`, and `usage` keep bounded notification snapshots from `fs/changed`, fuzzy file search, and rate-limit updates; `skills`, `plugin`, `crew`, and `config` are read from app-server list/read methods at render time. `crew` keeps collab tool-call lifecycle in Cradle's provider snapshot and resolves receiver thread ids through app-server `thread/read` so Runtime surfaces can show Codex-owned subagent nickname, role, title, preview, and model provider when available. Cradle stores only the provider snapshot needed to replay those projections across composer state, slash command rows, toolbar option summaries, Right Aside Runtime cards, and stream evidence blocks.

## Files

- `provider.ts`: Codex `ChatRuntime` implementation; starts/resumes app-server threads, fetches full app-server turn history for resumed native threads, projects app-server thread names and provider-owned UI slot states to Chat Runtime, injects reconstructed Cradle history through `thread/inject_items`, starts normal turns, activates provider-native goal continuations, streams notifications, and handles live steering/cancellation.
- `provider.test.ts`: Regression tests for Codex thread startup, provider title projection, provider config, transcript reconstruction, UI slot state projection, streaming, steering, cancellation, and diagnostics.
- `app-server-client.ts`: Newline-delimited JSON-RPC client for a per-turn Codex app-server process.
- `app-server-client.test.ts`: Client path and transport tests.
- `app-server-mapper.ts`: Maps Codex app-server notifications into AI SDK `UIMessageChunk` events carrying Cradle-owned tool envelopes. Reasoning items are projected only when Codex provides displayable `content`, `summary`, or reasoning deltas; encrypted-only reasoning is not surfaced as an empty UI part.
- `app-server-capabilities.ts`: Generated Cradle-owned manifest of the app-server client methods, server requests, and server notifications.
- `app-server-bridge.ts`: Generic session-scoped bridge for invoking any generated app-server method and streaming raw notifications as SSE.
- `tools/`: Codex tool identifier and app-server item payload mapper.
- `app-server-tool-payload.ts`: Compatibility re-export for Codex tool payload helpers owned by `tools/mapper.ts`.
- `native-history-projector.ts`: Projects full Codex app-server `Turn` snapshots into Responses API items for best-effort restoration when a fresh Codex thread replaces a previous native thread.
- `transcript-projector.ts`: Projects reconstructed Cradle transcript history into Codex Responses API items for native thread injection, unwrapping tool envelopes back to provider-native function-call names, arguments, and outputs.
- `ui-slots.ts`: Projects generated Codex app-server capabilities into provider-owned runtime UI slot descriptors.
- `app-server-protocol/`: Generated TypeScript bindings from `codex app-server generate-ts --experimental --out apps/server/src/modules/chat-runtime-providers/codex/app-server-protocol`. Do not edit generated files by hand.

## Regeneration

After regenerating `app-server-protocol/`, run `pnpm --filter @cradle/server generate:codex-app-server-capabilities` to refresh `app-server-capabilities.ts`. The capability generator derives method names and params from the generated protocol files, and keeps only Cradle-owned runtime semantics such as stream-capable methods in the generator.

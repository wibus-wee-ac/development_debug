# Features/Chat

Renderer-side view layer for chat.
Streaming updates arrive as AI SDK `UIMessageChunk` frames through a chat-owned transport abstraction. Ordinary web runtime uses server SSE directly. Electron Desktop runtime uses `window.cradle.chatStream`, where Electron main owns the long-lived upstream server SSE connection and renderer windows consume IPC fanout. Initial hydration and reload/recovery read trusted `UIMessage` snapshots through React Query and project locally into Zustand.
Passive windows hydrate the current message snapshot first, then subscribe through `chat-stream-transport.ts` for active-run AI SDK chunks instead of polling snapshots while a message is streaming. In web runtime this transport calls `GET /chat/sessions/{sessionId}/stream`; in Electron Desktop it subscribes to the main-process broker so multiple windows share one upstream stream. The passive chunk consumer always rebuilds the active assistant message from the replayed stream protocol instead of using the hydrated snapshot as AI SDK internal stream state, so late joins receive required part-start chunks before text/reasoning deltas even when the DB snapshot is still empty during streaming.
Codex active goals can create server-owned system continuation runs after a previous run fails or idles without user cancellation. The runtime status hook keeps polling while `/runtime-status` reports `hasActiveGoal`, and `use-chat-session.ts` refreshes message snapshots when runtime status exposes an active run message id that is not yet hydrated. Once the new streaming assistant row appears in the snapshot, the existing passive session-stream join path consumes the new run; no visible internal user message is added to chat history.
Text/reasoning/file parts hydrate as `UIMessage.parts`. Chat-owned structured context parts such as `$`-selected Skills are also stored in `UIMessage.parts` under the `data-cradle-*` namespace, rendered inline with the user prompt, and projected only by providers that understand them. Tool calls also stay in `UIMessage.parts`; chat render plans derive transient `messageId + partIndex` refs for subscriptions, but no browser-owned mirror stores tool payload by `toolCallId`.
The store preserves raw AI SDK `UIMessage.parts` as the message-history source of truth. Tool UI reads fields such as `approval`, `input`, `providerExecuted`, output state, and provider-specific payload directly from the current tool part so native AI SDK approval continuation and Cradle Tool UI standardization evolve on the same message boundary.
Native AI SDK tool approvals render inline from tool parts with `state: "approval-requested"`. Approve/deny actions update the tool part to `approval-responded`, use AI SDK `lastAssistantMessageIsCompleteWithApprovalResponses`, and continue by sending the complete `messages` history through the existing chat response endpoint. They do not use the deleted independent approval stream.
Claude Agent `TodoWrite` state is synthesized by the server adapter into persisted tool output `pluginState.todos`. Chat store selectors reverse-scan raw `UIMessage.parts` for the latest plugin state and render it in Right Aside runtime surfaces; inline `TodoWrite` blocks may still project directly from tool args while the call is running. The TODO shared vocabulary is `todo` / `processing` / `completed`, with processing text read from `activeForm`. Codex app-server plan/file/MCP/web tool items render through the same classified tool block surface. Claude Agent only exposes `bypassPermissions` and `plan` mode through Chat Runtime's permission-mode endpoint and a compact Composer segmented control; idle changes are sent with the next run, and streaming changes also call the active runtime side-channel.
Provider-owned UI slot state is consumed by the surface declared by the provider. Composer-adjacent rendering is reserved for slots with `composerState`, such as Codex goal; snapshot-style runtime metadata such as status, model, reasoning, MCP, alerts, skills, plugin, and config must not render as chips above the input or as synthetic message-bubble content. Message-stream events that need transcript placement should arrive as stream evidence or persisted message/tool parts instead of polled UI slot state. Codex compact state separates context-compaction lifecycle from thread token-usage meter state, so the `/compact` row can show running/completed lifecycle and current usage as an icon-ring state plus inline copy like `(used 52%)` without Cradle owning compaction semantics. Picker-style state such as model, reasoning, and config is exposed through a compact Composer toolbar option placeholder and existing model-picker surfaces, not by fake `/model` or `/reasoning` slash commands. Right Aside Runtime renders Cradle-owned workflow summaries such as Plan/TODO progress, run status, tools, and chat attention; Dev-only runtime environment diagnostics render from a top-right resource-style popover.
Subagent progress renders from parent tool outputs. Claude Agent subagent chunks arrive as preliminary AI SDK `tool-output-available` data containing `{ type: "cradle.subagent-output.v1", message }`; nested activity is read from that tool output instead of a client `parentToolCallId` routing map.
When a session is already streaming, the composer can submit a durable Chat Session
continuation item instead of starting a second run. The default mode comes from Chat
settings, `Shift+Meta/Ctrl+Enter` flips between `queue` and `steer` for one send, and the
visible queue controls cancel, drag/drop reorder, or button-reorder pending items through
chat-runtime endpoints while keeping running steer rows visible as non-reorderable status
items.
AI SDK wire validation is intentionally limited to the SSE boundary through `uiMessageChunkSchema`. Once a frame has been accepted as an AI SDK chunk or a snapshot has been loaded from Cradle's own database, chat feature code treats the object as trusted and uses direct TypeScript narrowing instead of feature-owned Zod schemas.

## Files

- **chat-tool-entities.ts**: Trusted tool-part helpers for reading AI SDK tool names, approval metadata, and nested SubAgent output from `UIMessage.parts` without materializing a parallel tool entity store
- **chat-capabilities.ts**: Feature-owned GET boundary for `/chat/draft-runtime-capabilities`, `/chat/sessions/{sessionId}/capabilities`, and `/chat/sessions/{sessionId}/ui-slot-states`, used only for runtime-native capability data and provider-owned slot state such as Codex compact, plan, tool activity, MCP, diff, terminal, approval, alert, filesystem, skills, plugin, search, crew, usage, and config summaries. The response is a Cradle-owned trusted API payload.
- **chat-context.ts**: Chat-owned attention snapshot store and Jarvis semantic context provider; publishes active chat attention state such as viewport range, scroll position bucket, near-bottom/manual-scroll state, and composer focus without exposing Chat DOM structure to system-agent, and exposes the same snapshot to Right Aside Runtime summaries.
- **chat-context.test.ts**: Unit coverage for Chat attention snapshot publication into typed Jarvis context envelopes
- **bang-command.ts**: Chat-owned parser for Composer `!cmd` submissions; accepts only single-line commands with no space after `!`, leaving empty, spaced, or multi-line input as ordinary chat text.
- **bang-command-metadata.ts**: Trusted metadata reader for Cradle-owned `metadata.cradle.bangResult` snapshots persisted by Chat Runtime.
- **chat-slash-commands.ts**: Web-owned slash command descriptor and merge helpers; converts runtime-native commands and command-like runtime UI slots into composer actions, annotates matching runtime slot command rows with provider-owned state labels, filters picker/metadata slots out of the slash panel, maps provider-native Codex slots such as compact and review onto submit/UI actions while leaving provider text commands such as feedback as raw slash text, supplies fallback runtime command descriptors for pre-session composer surfaces, registers Cradle UI commands such as `/appshot`, and keeps Cradle UI commands separate from provider capabilities
- **message-bubble.tsx**: Store-backed and direct message bubble renderer with execution folding, tool approval actions, copy controls, Codex goal message presentation, bang command result presentation, and tool blocks subscribed by `messageId + partIndex`. It renders persisted message content and stream-derived tool evidence directly from `UIMessage.parts`, but does not inject polled runtime UI slot snapshots into assistant bubbles.
- **chat-response-command.ts**: Feature-owned HTTP command boundary for `/chat/sessions/{sessionId}/response`, `/chat/sessions/{sessionId}/bang-command`, `/chat/sessions/{sessionId}/stream`, `/chat/sessions/{sessionId}/cancel`, `/chat/sessions/{sessionId}/permission-mode`, and `/chat/sessions/{sessionId}/queue`; long-lived response/stream calls are now consumed through `chat-stream-transport.ts` so Electron can replace renderer-owned SSE with desktop IPC fanout while web runtime keeps the same HTTP path. Response and queue bodies may include chat-owned `contextParts` such as selected Skills.
- **prompt-ingress.ts**: Chat-owned session-scoped prompt ingress registry used by host surfaces such as Browser Panel webviews; external page requests are converted to `FileUIPart[]` by their host surface and finally submit through the mounted ChatView composer send path.
- **prompt-ingress.test.ts**: Regression coverage for session-scoped prompt ingress routing, unregister behavior, and cleanup ordering when a ChatView remount replaces a handler.
- **chat-stream-transport.ts**: Chat-owned transport abstraction for starting response streams and joining active session streams. It chooses Electron main-process IPC when `window.cradle.chatStream` is available, buffers early IPC events until the renderer stream is attached, validates incoming chunks with AI SDK `uiMessageChunkSchema`, and falls back to the existing HTTP SSE parser outside Electron.
- **chat-stream-transport.test.ts**: Regression coverage for Electron event-backed stream creation, Electron error propagation, and HTTP SSE fallback behavior.
- **chat-continuation-metadata.ts**: Chat-owned reader and optimistic message factory for `metadata.cradle.continuation`, keeping queue/steer presentation metadata separate from provider-visible message parts while preserving selected context parts in visible continuation messages.
- **chat-queue-list.tsx**: Shared compact continuation queue list with localized mode/status badges, drag/drop reorder, up/down button reorder, pending-item cancellation controls, and read-only running steer visibility.
- **chat-runtime-view.tsx**: Chat session runtime boundary shared by normal tab routes and the dedicated Electron tear-off renderer, passing runtime and bound-agent ownership into chat rendering while keeping chat rendering independent from the main app shell and tab registry.
- **chat-session-prefetch.ts**: Chat-owned prefetch boundary for opening existing sessions; navigation surfaces call this helper to preload the Chat view chunk plus session metadata and transcript snapshots without owning chat query keys.
- **chat-todo-projection.ts**: Chat-owned TODO plugin-state reader and inline TodoWrite projection model; session surfaces read persisted `pluginState.todos`, while tool blocks can map live tool args into the same `todo` / `processing` / `completed` vocabulary.
- **use-session-todos.ts**: Session-level selector hook that scans persisted `UIMessage.parts` from newest to oldest and exposes the latest adapter-synthesized TODO snapshot for the Right Aside runtime surface.
- **runtime-session-status-command.ts**: Chat-owned HTTP reader for server-owned `/chat/sessions/{sessionId}/runtime-status` data, including active-goal discovery state, used by runtime status surfaces.
- **use-runtime-session-status.ts**: React Query hook for server-owned runtime session status with light polling while a run is active, pending, cancelling, or an active Codex goal can create a background continuation run.
- **runtime-diagnostics-popover.tsx**: Dev-only top-right chat popover for resource-panel-style provider environment diagnostics such as status, model, reasoning, MCP, skills, plugins, usage, and config.
- **runtime-session-panel.tsx**: Right Aside runtime panel for the selected chat session; merges provider Plan slot state and adapter TODO snapshots into one Progress task surface, renders provider-projected crew/subagent state, then summarizes chat attention, server-owned runtime status, UI-visible status, runtime/provider/session identity, latest run timing, queue counts, and recent tool-call state derived from current message parts.
- **runtime-ui-slot-panel.tsx**: Provider-owned UI slot card renderer for chat runtime diagnostics; groups provider-declared `runtimePanel` slot states into environment, activity, and available sections while leaving Goal, Compact, and Plan to their primary chat workflow surfaces.

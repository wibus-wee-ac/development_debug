title: Migrations
description: Drizzle migration artifacts, journal integrity, baseline history, and validation contracts.

Migration files 是兼容性 artifact，不是格式化输出。应把它们视为 local workspace 和 server state 的 durability contract。

当前迁移历史已在首次个人/公开使用前重新基线化为 `0000_initial_release_baseline.sql`。在没有任何需要保留的外部用户数据前，可以重建 baseline；一旦 release 边界成立，后续 schema 变化只能追加 migration，不要再重写历史。

## 谁负责

`packages/db` owns migration layout and schema export compatibility. Each domain owner owns the migration content for its tables.

## 放在哪里

- SQL migrations：`packages/db/drizzle/*.sql`
- Drizzle journal：`packages/db/drizzle/meta/_journal.json`
- Snapshots：`packages/db/drizzle/meta/*.json`
- Schema source：`packages/db/src/schema/**`

## 怎么运行

1. Update Drizzle schema.
2. Generate or author migration using the repository-approved command.
3. Review SQL for owner namespace and destructive behavior.
4. Keep journal and snapshots in sync.
5. Add or update migration tests.
6. Run server database lifecycle tests.

## Review 要看什么

Every migration review should ask:

- Does the migration write only to the owner namespace?
- Does it preserve existing local data?
- Does it have a rollback or recovery story if it is destructive?
- Does it keep derived read models separate from canonical tables?
- Does it update tests and docs for public behavior changes?

## 怎么验证

```bash
cd apps/server
pnpm test -- database
```

If `packages/db` exposes package tests, run them too:

```bash
cd packages/db
pnpm test
```

## 边界

The current baseline was generated with:

```bash
pnpm exec drizzle-kit generate --name initial_release_baseline
```

Use this only when intentionally resetting a pre-release database history. For normal schema changes after the release boundary, use the same Drizzle generation flow with a migration-specific name and append to the existing journal.

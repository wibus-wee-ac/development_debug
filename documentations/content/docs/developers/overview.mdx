Cradle 的开发者文档按能力 owner 组织。每个页面回答同一组问题：谁拥有语义，写入哪个 namespace，生命周期如何推进，哪些 route 或 command 是稳定入口，如何验证，哪些边界不能越过。

<DeveloperArchitectureMap />

## 核心原则

Cradle 可以读取其他产品或生态的 namespace 来保持兼容，但不能把写入语义放到不属于 Cradle 的 namespace。跨 namespace 写入必须由目标 owner 提供明确 API，否则视为禁止模式。

这个原则适用于 server module、plugin、database schema、generated CLI、automation 和 desktop integration。文档中的 owner 不是目录名装饰，而是迁移、兼容、错误处理和权限边界的责任归属。

## 页面应该说明什么

每个能力页都应尽量列出：

- `Owner`：语义、兼容、迁移、错误语义的负责方。
- `Namespace`：持久化路径、database tables、route prefix 或 capability identity。
- `Lifecycle`：registration、activation、execution、cleanup、upgrade 或 migration。
- `Interfaces`：HTTP routes、WebSocket routes、CLI commands、environment variables。
- `Validation`：测试、typecheck、build 或人工检查。
- `Boundaries`：非目标、HTTP-only surface、in-memory surface，以及应该交给相邻 owner 的部分。

## 需要确认的边界

这些点需要在实现或发布前继续确认，页面会先把它们写成边界，而不是写成用户已经能依赖的能力：

- `src/cli/**` 是否仍是支持入口；当前开发者文档以 `packages/cli/**` 为 canonical generated CLI。
- plugin storage 的持久化语义需要和 host 实现保持一致；在确认前，只把它描述为 host 暴露的 `storage` capability。
- web 和 desktop plugin loader 的完整 lifecycle 需要结合 app 代码验证；页面先描述 SDK 和 host 已经给出的边界。
- database migration generation command 需要和 `packages/db/package.json` 对齐；页面先记录 migration artifacts 和验证方向。

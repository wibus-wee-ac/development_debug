---
title: HTTP foundation
description: Request context, errors, validation, OpenAPI exposure, and HTTP foundation contracts.
---

HTTP foundation 是 server module 共享的边界。它负责请求身份、错误形状、验证行为、日志、CORS 和 API 文档暴露。业务 module 不应绕开这些基础层实现自己的并行协议。

## 谁负责

`apps/server/src/http/**` 拥有 HTTP cross-cutting behavior。module owner 负责业务错误语义，但最终 HTTP status、error envelope 和 validation response 由 HTTP foundation 统一映射。

## 放在哪里

- OpenAPI UI：`/docs`
- OpenAPI document：`/openapi.json`
- OpenAPI alias：`/docs/openapi.json`
- Session provenance header：`x-cradle-chat-session-id`

`x-cradle-chat-session-id` 用于把 runtime 请求和当前 chat session 关联。它不是通用 auth token，也不应被文档描述成跨服务身份凭证。

## 怎么运行

1. 请求进入 server。
2. foundation 分配或传播 request id。
3. actor context 从 headers 和 runtime context 派生。
4. route schema 执行 validation。
5. module handler 执行业务逻辑。
6. exception filter 把已知错误映射成结构化 response。
7. request logger 记录请求结果。

## 错误契约

文档页和 route examples 应保持同一原则：

- validation error 是 client contract failure。
- module domain error 由 module owner 命名，但 envelope 由 HTTP foundation 维护。
- unexpected error 不泄漏内部 stack。
- request id 应可用于日志关联。

具体字段名以 `apps/server/src/http/error-mapping.ts` 为准。新增字段前先更新代码、测试和 OpenAPI examples，再同步页面。

## 怎么验证

相关测试入口：

```bash
cd apps/server
pnpm test -- request-id
pnpm test -- exception-filter
pnpm test -- elysia-skeleton
```

如果测试 runner 不支持 pattern 参数，使用完整 server test suite：

```bash
cd apps/server
pnpm test
```

## 边界

HTTP foundation 不拥有业务权限模型、database ownership 或 CLI command naming。新增 route 时，应在 module 内定义 schema 和 `x-cradle-cli` metadata，再让 OpenAPI 和 CLI generator 消费这些 metadata。

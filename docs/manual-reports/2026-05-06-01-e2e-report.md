  问题： 约 25 个 Then 步骤只做 toBeVisible() 检查，无法捕获数据绑定错误、内容渲染错误、状态转换错误。

  示例：
  - agent-identity.steps.ts 的 4 个 Then 中有 3 个纯 visibility
  - agent-runtime-settings.steps.ts 的 3 个 Then 全部是 visibility
  - kanban.steps.ts 的 看板视图应显示 只检查容器可见

  建议： visibility 断言作为 smoke 可以保留，但每个 feature 至少 50% 的 Then 步骤应验证数据内容或状态属性。

  4.2 When/Then 边界违规

  问题： 两个 step 文件在 When 步骤中执行断言：
  - kanban.steps.ts — 我点击Comment按钮 注册为 When 但检查了 textarea 是否清空
  - workspace.steps.ts — 我点击"移除工作区" 注册为 When 但断言了 count = 0

  建议： 将断言拆到独立的 Then 步骤，保持 Given/When/Then 语义清晰。

  4.3 DB 持久化验证仅限 chat

  问题： 只有 chat.steps.ts 通过 better-sqlite3 直接查询数据库验证持久化。其他所有 feature（agents、kanban、skills、workspaces、providers）完全不查 DB。

  影响： UI 可能正确渲染了数据，但底层没有持久化——或者持久化了错误的值——测试无法发现。

  建议： 为以下场景添加 DB 验证：
  - Agent 创建后查 agents 表
  - Provider profile 创建后查 agent_profiles 表
  - Issue 创建/移动/删除后查 kanban_issues 表
  - Workspace 创建后查 workspaces 表

  七、总结

  你的直觉是对的。 整体 43 个场景中：
  - ~18 个（42%） 有真实行为断言（DB 查询、文件系统验证、状态属性检查）
  - ~15 个（35%） 是 moderate 断言（文本内容、count delta）
  - ~10 个（23%） 是纯 visibility 断言，几乎无法捕获回归

  最强的 chat 模块测到了 DB timeline 事件序列级别，最弱的 agent-identity 连"创建一个 Agent"这个主流程都没测完。从"能打开页面"到"能完成业务流程"之间有一个巨大的断层，这个断层集中在 Agent
  管理、Provider 配置、Kanban 操作三个核心模块。

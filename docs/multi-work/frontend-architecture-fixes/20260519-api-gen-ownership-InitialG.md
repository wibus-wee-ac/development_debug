# API Gen Ownership InitialG Handoff

## Problem Statement

`apps/web/src/api-gen` is currently required by frontend source but is not a tracked source tree.

Concrete evidence:

- `apps/web/.gitignore` ignores `src/api-gen/` and documents it as a generated API client.
- `apps/web/openapi-ts.config.ts` writes generated output to `./src/api-gen` with `clean: true`.
- The generator input is `http://localhost:21423/openapi.json`, so generation requires a running local server.
- `apps/web/package.json` exposes `generate: openapi-ts`.
- Root `package.json` exposes `generate:web`, `typecheck:apps-web`, and `build:web`, but `typecheck:apps-web` and `build:web` do not run generation first.
- Web source imports generated modules directly, for example `~/api-gen/sdk.gen`, `~/api-gen/@tanstack/react-query.gen`, and `~/api-gen/types.gen`.
- The earlier web migration plan explicitly described `apps/web/src/api-gen/` as gitignored and regenerated by `pnpm generate`.

The unresolved ownership issue is not whether generated code exists. The issue is that the repository currently treats the generated client as a local artifact while also making normal web typecheck/build depend on that artifact already existing. That is fragile for fresh clones, CI, and reviewers.

The ownership boundary should be:

- `apps/server` owns the API contract semantics and OpenAPI document shape.
- `apps/web` owns the generated TypeScript client output and how frontend code consumes it.
- Root scripts or CI own orchestration across server contract export, client generation, and web validation.

## Options

### Option 1: Commit `apps/web/src/api-gen`

Remove the ignore rule and treat generated client files as reviewed source artifacts.

Pros:

- Fresh clones can typecheck and build `@cradle/web` without running a server.
- API client diffs become visible in code review.
- CI can fail on unstaged generated diffs after contract changes.

Cons:

- Generated churn increases review noise.
- `output.clean: true` means generator version changes can rewrite a large tree.
- The web namespace would contain a large derived artifact whose semantics are still owned by server routes and OpenAPI metadata.
- It encourages manual inspection of generated code instead of validating the server contract and generated surface.

Risk:

- Moderate. It is operationally simple, but it weakens the current repo intent and creates persistent generated-code churn.

### Option 2: Keep `apps/web/src/api-gen` ignored and generate from a live server

Keep the current policy, but document that contributors must start `apps/server` and run `pnpm generate:web` before web typecheck/build.

Pros:

- Minimal immediate change.
- Matches the current `apps/web/openapi-ts.config.ts` input.
- Keeps generated output out of commits.

Cons:

- Fresh clone and CI remain dependent on an implicit bootstrap step.
- CI must manage a live server process just to typecheck web.
- Contract generation becomes timing-sensitive: local database/env/server startup issues can block client generation even when only static OpenAPI output is needed.
- Root `typecheck` can still fail if generation was skipped.

Risk:

- High. This preserves the current failure mode with only better documentation.

### Option 3: Keep `apps/web/src/api-gen` ignored, but generate from a server-owned schema artifact

Keep generated TypeScript output local and untracked, but move the generator input away from an always-live localhost dependency. Add a server-owned way to materialize the OpenAPI document, then make web generation consume that artifact in CI/bootstrap.

Example ownership shape:

- `apps/server` provides a deterministic contract export command that writes an OpenAPI JSON artifact under a Cradle-owned generated/cache location.
- `apps/web` keeps `src/api-gen/` ignored and regenerates it from that artifact.
- Root orchestration runs contract export before `generate:web`, and runs generation before web typecheck/build in CI or aggregate validation.

Pros:

- Preserves the current intent that `apps/web/src/api-gen` is generated and uncommitted.
- Removes the need for an already-running local server in static validation paths.
- Keeps contract ownership with `apps/server`.
- Keeps generated client lifecycle with `apps/web`.
- Gives CI a deterministic pipeline: export schema, generate client, typecheck/build.

Cons:

- Requires a small cross-package workflow change.
- Requires a decision about where the materialized OpenAPI artifact lives and whether it is tracked.
- Requires updating docs/scripts so developers do not run stale generated clients by accident.

Risk:

- Moderate. It touches orchestration and possibly server tooling, but it aligns with the namespace ownership rule better than committing generated client output.

### Option 4: Move generated client into a shared package

Create a workspace package such as `packages/api-client` and have web import from it.

Pros:

- Makes the generated client a named package boundary.
- Could support future non-web consumers.

Cons:

- Adds a new ownership namespace before there is evidence of multiple consumers.
- Does not solve schema export or bootstrap by itself.
- Increases package graph and review surface.

Risk:

- Medium to high for this pass. This is premature unless another app needs the same generated client.

## Recommended Decision

Choose Option 3.

`apps/web/src/api-gen` should remain an ignored local generated artifact, but generation should not depend on an already-running localhost server for normal validation. The server should own exporting the OpenAPI contract, and the web app should own generating its client from that exported contract.

This is the cleanest fit for Cradle's namespace rule:

- Web can read the server-owned contract.
- Web should write only to its own generated client namespace.
- Server should not write into `apps/web/src/api-gen`.
- Root scripts can coordinate cross-owner validation without claiming semantic ownership of either side.

The immediate conclusion is architectural, not a request to patch business code inside this worker. The current state should not be left as "ignored generated files plus no standard bootstrap." Either CI must generate them before web validation, or the files must be committed. The better long-term default is uncommitted generated output backed by a deterministic schema export.

## Risks

- Stale local clients: developers may keep an old `src/api-gen` directory and not notice contract changes unless scripts regenerate before validation.
- Contract export drift: if the server export command and live `/openapi.json` route diverge, CI may validate a different contract than the running app serves.
- Hidden generated type errors: `apps/web/tsconfig.json` excludes `src/api-gen/**`, so generated files themselves are not directly typechecked as source. Import-site typechecking catches many issues, but malformed generated internals can still be harder to diagnose.
- Dirty tree coordination: `apps/web/package.json` is already modified by WorkerD, and other workers own nearby frontend changes. Any script changes should be merged carefully rather than overwritten.
- Server readiness: if no deterministic OpenAPI export command exists today, adding one may require server-side work outside the frontend architecture fix ownership.
- Review scope: changing root validation scripts affects all contributors and CI jobs, so it should be reviewed as workflow infrastructure, not as a local UI cleanup.

## Rollout Steps

1. Confirm the ownership decision in the frontend architecture fix plan decision log.

2. Keep `apps/web/src/api-gen/` ignored unless the team explicitly rejects generated-at-bootstrap.

3. Add or identify a server-owned OpenAPI export path.

   The export should produce the same schema as `http://localhost:21423/openapi.json` without requiring a long-running dev server. The artifact location should be under a Cradle-owned generated/cache path, not inside another product's namespace.

4. Update `apps/web/openapi-ts.config.ts` to support artifact input for CI/bootstrap.

   A practical shape is to read an environment-provided schema path when present and fall back to the existing local URL for manual dev generation.

5. Add explicit root orchestration.

   Root validation should expose a command that performs:

   ```bash
   pnpm <server-openapi-export-command>
   pnpm generate:web
   pnpm typecheck:apps-web
   ```

   `build:web` should either depend on generation or CI should call a documented prebuild command before it.

6. Add stale-client protection.

   CI should fail if generating the client from the exported contract fails. If a schema artifact is tracked, CI should also detect when it is stale. If the artifact is untracked, CI should at least run generation in a clean workspace before typecheck/build.

7. Document the workflow.

   Update the relevant web/server README or plan outcome with:

   - who owns the server contract,
   - who owns `apps/web/src/api-gen`,
   - how to regenerate locally,
   - which command CI uses,
   - whether a live server is optional or required for manual generation.

8. Defer a shared `packages/api-client` until there is a second real consumer.

## Validation

Validation for the final implementation should prove both reproducibility and ownership boundaries.

Required checks:

```bash
pnpm <server-openapi-export-command>
pnpm generate:web
pnpm --filter @cradle/web exec tsc --noEmit
pnpm --filter @cradle/web build
```

Recommended workflow checks:

```bash
git status --short --ignored -- apps/web/src/api-gen
git diff --check -- apps/web/.gitignore apps/web/openapi-ts.config.ts apps/web/package.json package.json
```

Expected outcomes:

- `apps/web/src/api-gen/` remains ignored if Option 3 is adopted.
- `pnpm generate:web` succeeds without requiring a manually started server in CI/bootstrap mode.
- Web typecheck/build succeed after generation in a clean workspace.
- Root validation no longer depends on a pre-existing local `apps/web/src/api-gen` directory.
- Server contract export and live `/openapi.json` are either generated by the same code path or covered by a test that prevents drift.

Manual sanity checks:

- Delete only the local generated client directory, regenerate, and verify web typecheck can recover.
- Change a server route schema in a small controlled branch, export the contract, regenerate the web client, and confirm the generated API surface changes predictably.
- Verify no server workflow writes directly into `apps/web/src/api-gen`; web generation should be the only writer for that directory.

## Initial Conclusion

The architecture should not commit generated web client files by default, and it should not keep relying on an implicit live localhost server for normal validation. Treat the OpenAPI document as a server-owned contract artifact and `apps/web/src/api-gen` as a web-owned generated cache. Then wire root-level validation so generation is explicit, repeatable, and required before web typecheck/build.

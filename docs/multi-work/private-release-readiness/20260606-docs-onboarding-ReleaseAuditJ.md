# Private Release Readiness Audit J: Documentation And Onboarding

Date: 2026-06-06

Scope: documentation, onboarding, tester instructions, first-run UX docs, and private release operational readiness.

Constraints: read-only audit for source files; source files were not modified. This handoff file is the only written artifact.

Excluded: notarization and signing documentation, except where missing unsigned/private tester install instructions would block invited testers.

## Summary

Cradle is not documentation-ready for invited private testers. The main blocker is not a lack of product documentation in general; the repository has broad user docs, Fumadocs content, troubleshooting pages, support/export notes, and release notes. The blocker is that no tester-facing document gives a concrete private release path from invite to installed app to first successful session.

The current top-level and quick-start paths either send users to GitHub releases without private-channel context, or tell them to run development commands. Provider setup is also too abstract for a first successful chat, and support/export instructions are split between `Settings > Support` and Devtools paths.

## Findings

### Critical: invited testers have no concrete private install path

Evidence:

- `README.md:8` links to `https://github.com/wibus-wee/Cradle/releases` as `Download Latest Release`, but there is no private channel name, artifact naming convention, platform matrix, checksum expectation, or invite-specific instruction.
- `docs/for-users/quick-start.md:5-21` starts with `pnpm install`, `pnpm dev`, and then says packaged builds use an app bundle generated by a target build command. This is developer onboarding, not tester onboarding.
- `documentations/content/docs/getting-started/desktop-app.mdx:12-16` says to use the installed desktop app, but does not say where invited testers obtain it, which artifact to choose, or what the expected first launch looks like.
- `documentations/content/docs/index.mdx:18-73` routes users through desktop app, workspace, composer, providers, and troubleshooting, but does not include an installation/download step.
- `docs/for-users/preview-release-notes.md:31-38` defines a distribution gate for signed/notarized public-style artifacts, but does not provide a private tester install flow or fallback path.

Impact:

Invited testers cannot reliably answer "what do I download, how do I install it, and what should I expect on first launch?" without out-of-band instructions. That blocks a private release test because the first support load will be distribution confusion rather than product feedback.

Confidence: High.

### High: quick-start build commands are inaccurate for the actual package scripts

Evidence:

- `docs/for-users/quick-start.md:21` names `pnpm build:mac`, `pnpm build:win`, and `pnpm build:linux`.
- Root `package.json:24-26` only defines `build:web`, `build:server`, and `build:desktop`; it does not define `build:mac`, `build:win`, or `build:linux`.
- `apps/desktop/package.json:20-24` defines the actual platform packaging commands as `dist`, `dist:publish`, `dist:mac`, `dist:win`, and `dist:linux`.
- `apps/desktop/scripts/README.md:18-20` documents `pnpm --filter @cradle/desktop pack`, `dist:mac`, and `dist:publish`, matching the package scripts.

Impact:

If a tester or release operator follows the quick start for packaged builds, the example commands fail immediately. This damages confidence in the release instructions and can block local reproduction of install/update issues.

Confidence: High.

### High: first successful provider/chat path lacks concrete configuration examples

Evidence:

- `docs/for-users/quick-start.md:31-49` says to add provider profiles such as `openai-compatible`, `acp-chat`, or `cli-tui`, bind agents, select provider/model, and send a prompt, but does not provide a minimal known-good configuration.
- `documentations/content/docs/agents/providers.mdx:12-20` says to fill credentials and endpoint, enable the profile, and run health check, but does not define required fields for even one supported provider kind.
- `documentations/content/docs/agents/models.mdx:12-15` only says to select a provider then a model, and to refresh provider model cache if missing.
- `documentations/content/docs/agents/runtime-kinds.mdx:14-19` names Provider-backed, CLI TUI, and ACP, but does not map them to required provider/profile fields or first-test expectations.
- `documentations/content/docs/troubleshooting/provider-errors.mdx:54-56` explicitly falls back to "look at the current Settings UI" and the provider console for token, endpoint, and model names.

Impact:

The release notes promise that a configured OpenAI-compatible provider can create a workspace-backed chat session, but the docs do not show how to create that provider in a repeatable way. Private testers can get stuck before the first model response, especially if the Settings UI labels differ from the docs or if model discovery does not return a list.

Confidence: High.

### High: there is no private release test plan or tester feedback checklist

Evidence:

- `docs/for-users/preview-release-notes.md:7-13` lists what works in the preview, but it is descriptive release scope, not a tester task list with pass/fail expectations.
- `docs/for-users/quick-start.md:62-69` has a brief "Validate Core Features" list, but it omits install success, first-run empty state, provider health, first chat output, diagnostics export, update check, data reveal, uninstall/retained data, and feedback submission expectations.
- `documentations/content/docs/troubleshooting/index.mdx:48-57` lists evidence to collect after problems occur, but there is no linked pre-release testing script that tells testers what to exercise and what evidence to attach.
- Existing readiness handoffs under `docs/multi-work/private-release-readiness/` are internal audit artifacts, not tester-facing instructions.

Impact:

Even if testers can install and start Cradle, the team will receive inconsistent feedback. Some testers may only explore the UI; others may validate chat or updates; support reports may lack version, platform, session ID, diagnostics bundle, or exact reproduction steps.

Confidence: High.

### Medium: support and diagnostics instructions are inconsistent across user docs and documentation site

Evidence:

- `docs/for-users/end-user-guide.md:153-159` describes `Settings > Support` as the preview support entry for diagnostics export, feedback template copy, feedback channel open, data reveal, and uninstall notes.
- `docs/for-users/troubleshooting.md:167-178` also instructs users to export diagnostics from `Settings > Support`.
- `docs/for-users/data-model-and-storage.md:180-184` says `Settings > Support` exposes storage location and diagnostics export.
- `documentations/content/docs/troubleshooting/devtools-export.mdx:24-30` instructs users to open Devtools, go to Observability, and export a bundle.
- `documentations/content/docs/operations/observability.mdx:8-11` says Devtools can export diagnostics bundles.
- `documentations/content/docs/operations/settings.mdx:12-23` lists settings sections but omits Support entirely, despite the user docs treating Support as the primary preview support surface.

Impact:

Testers following different docs will use different evidence paths. If Support is the intended private-preview flow, the Fumadocs site under-documents it; if Devtools export is also supported, the docs should explain when to use each path and whether both produce the same artifact.

Confidence: High.

### Medium: first-run UX docs do not match private release expectations

Evidence:

- `apps/web/src/features/onboarding/README.md:3` describes onboarding as a development-only first-run overlay with mock data and local preview choreography.
- `docs/for-users/preview-release-notes.md:9-10` says fresh start from an empty profile shows real empty states and New Chat explains missing setup steps.
- `documentations/content/docs/getting-started/overview.mdx:47-58` says to configure provider and select workspace/runtime/provider/model, but does not document the actual empty-state sequence testers should see when no workspace or provider exists.
- `documentations/content/docs/getting-started/first-workspace.mdx:12-19` describes adding a workspace but not the first-run empty state, permissions prompts, failure messages, or success criteria.

Impact:

Private testers cannot distinguish expected first-run empty states from missing data, broken onboarding, or disabled mock onboarding. This raises support noise around the exact area the preview claims to validate.

Confidence: Medium-High.

### Medium: user-facing docs are split between `docs/for-users` and `documentations/content/docs` without a clear canonical source

Evidence:

- `docs/for-users/README.md:1-17` presents `docs/for-users` as the end-user and integration-developer documentation set.
- `documentations/content/docs/index.mdx:8-16` presents the Fumadocs content as the user journey entry.
- `README.md:1-61` links only to GitHub releases and does not link to either user documentation set.
- `docs/README.md:23` inventories `docs/for-users`, but the site navigation in `documentations/content/docs/meta.json:3-17` is separate and does not include preview release notes or the `docs/for-users` quick start.

Impact:

Release operators can choose one docs set while testers discover another. This creates drift: the richer private-preview Support notes live in `docs/for-users`, while the website entry lacks equivalent support/install detail.

Confidence: High.

### Low: server architecture docs are stale and may mislead technical testers

Evidence:

- `apps/server/README.md:3-5` still says the HTTP server is built on Tsuki/Hono and that Elysia is a parallel migration path with only a first feature slice.
- `apps/server/README.md:64-68` says only health and preferences are migrated route factories.
- Other readiness audit evidence already notes current `apps/server/src/app.ts` registers many Elysia modules directly. This finding is repeated here only because technical private testers may read app docs while debugging server startup.

Impact:

This is not a primary invited-tester blocker, but it will slow technical triage and can make testers inspect the wrong server path.

Confidence: Medium.

## Positive Signals

- `docs/for-users/end-user-guide.md` covers daily workflows, workspace/session behavior, support, diagnostics, data reveal, and share/export boundaries.
- `docs/for-users/troubleshooting.md` has practical recovery sections for CLI, streaming, TUI, workspace search, delegation, usage, settings cache, diagnostics export, data reveal, and uninstall.
- `docs/for-users/data-model-and-storage.md` clearly distinguishes Cradle-owned data from user workspace files and warns about retained data.
- `documentations/content/docs/troubleshooting/index.mdx` provides a useful boundary-based troubleshooting map.
- `documentations/content/docs/troubleshooting/provider-errors.mdx` has a compact provider error table and points users toward health check/model discovery.
- `apps/desktop/scripts/README.md` correctly documents the desktop packaging/update env path for release operators.

## Recommended Documentation Gates

1. Add a private tester install guide with platform artifact names, where to download, expected launch flow, first-run checks, data retention, and feedback channel.
2. Replace or split `docs/for-users/quick-start.md` so testers see packaged-app instructions first, while developer source startup remains clearly marked as developer-only.
3. Add a minimal provider setup recipe for the recommended private-test provider path, including required fields, model entry, health check success, and first chat prompt.
4. Add a tester checklist covering install, first launch, workspace add, provider health, first chat, session export, diagnostics export, update check, data reveal, retained-data/uninstall, and feedback submission.
5. Make `Settings > Support` versus Devtools export canonical: document which path testers should use and when.
6. Choose one canonical user-doc source for private release and link it from `README.md`, release notes, and the documentation site.

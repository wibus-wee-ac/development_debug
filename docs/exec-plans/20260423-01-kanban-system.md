## Purpose / Big Picture

After this change, a user can create Kanban boards inside Cradle to track development tasks (Issues) associated with their local workspaces. A user can open the Kanban section from the sidebar, create boards for a workspace, define custom status values (columns), file Issues, assign them to milestones, create sub-issues, move cards between columns by changing the Issue's status, and view Issue details (including comments) in a side panel — all without leaving the app.

The scope of this plan is deliberately self-contained: no Agent integration, no cross-workspace boards (deferred). The persistence layer is SQLite via Drizzle ORM, the IPC contract follows the existing `IpcService` / `@IpcMethod()` pattern, and the UI follows the existing feature-based component structure with TanStack Router routes.

A human can verify success by:

1. Opening the app, clicking the new Kanban entry in the sidebar, and seeing a "no boards yet" empty state.
2. Creating a board for a workspace, adding status columns (e.g. "Backlog", "In Progress", "Done"), and creating Issues that appear as cards.
3. Dragging a card to another column (or clicking a status toggle in the side panel) and observing the Issue's status update persist across app restarts.
4. Opening an Issue's side panel, editing the title/description/priority, adding a comment, creating a sub-issue, and assigning a milestone.

## Context and Orientation

Cradle is an Electron desktop app structured as three processes:

- `src/main/` — the Node.js main process, owns SQLite persistence (via Drizzle ORM + better-sqlite3), all IPC handlers, and any OS-level calls.
- `src/preload/` — a thin bridge that exposes typed IPC methods to the renderer via `contextBridge`.
- `src/renderer/` — React (TypeScript + Tailwind) UI, organised into `routes/`, `features/`, `components/`, `store/`, `hooks/`, and `lib/`.

The IPC pattern used throughout this repo is:

1. **Main process**: define a class extending `IpcService` and decorate async methods with `@IpcMethod()`. Register the class in `createServices([...])` inside `src/main/index.ts`.
2. **Type surface**: add `myService: typeof MyService` to the `IpcServices` type map in `src/main/ipc-types.ts`.
3. **Renderer**: call `window.ipc.myService.myMethod(arg)` — the client proxy is generated by `createIpcProxy` in `packages/ipc/src/client.ts` and bridged by the preload.

The database pattern is:

1. Define tables in `src/main/db/schema.ts` using Drizzle's `sqliteTable` / `text` / `int` builders.
2. Run `pnpm drizzle-kit generate` to produce a new SQL migration file under `drizzle/`.
3. At runtime `initDb()` in `src/main/db/index.ts` applies pending migrations automatically.

Route pattern:

1. Create a new file under `src/renderer/src/routes/` with a name matching TanStack Router's file-based convention (e.g. `kanban.tsx` for `/kanban`, `kanban.$boardId.tsx` for `/kanban/$boardId`).
2. Run `pnpm exec tanstack-router-cli generate` (or the app's dev server does this automatically) to regenerate `src/renderer/src/routeTree.gen.ts`.

## Data Model

The Kanban system maps onto five new SQLite tables. The existing `workspaces` table serves as the top-level container (workspace === project in Kanban terminology; no separate "project" table is needed).

### kanban_statuses

Represents the ordered set of possible status values for Issues in a workspace. Visually these become the columns of any Kanban board scoped to that workspace. Users can add, rename, reorder, and delete statuses.

Fields: `id` (text PK), `workspace_id` (→ workspaces, cascade delete), `name` (text), `color` (text, nullable — a CSS hex color or Tailwind token for column header tinting), `order` (integer — display order left-to-right), `created_at` (int unix epoch).

### kanban_boards

A named, persisted view into the Issues of a workspace. A board carries an optional `filter_config` JSON blob that defines which Issues are visible (filter by milestone ID, label strings, and/or priority values). Multiple boards can exist per workspace.

Fields: `id` (text PK), `workspace_id` (→ workspaces, cascade delete), `name` (text), `filter_config` (text, nullable — JSON), `created_at` (int), `updated_at` (int).

### kanban_milestones

A grouping entity with an optional deadline. Issues can be assigned to a milestone; milestone status (`open` / `closed`) can be toggled manually. Used as a filter dimension on boards.

Fields: `id` (text PK), `workspace_id` (→ workspaces, cascade delete), `title` (text), `description` (text, nullable), `due_date` (int, nullable — unix epoch), `status` (`open` | `closed`, default `open`), `created_at` (int), `updated_at` (int).

### kanban_issues

The core entity. An Issue belongs to a workspace and optionally to a status, a milestone, and a parent Issue (for sub-issues). The `status_id` may be null when an Issue has not been placed on any column yet (treated as "unassigned" / backlog).

Fields: `id` (text PK), `workspace_id` (→ workspaces, cascade delete), `status_id` (→ kanban_statuses, set null on delete, nullable), `milestone_id` (→ kanban_milestones, set null on delete, nullable), `parent_issue_id` (self-reference → kanban_issues, set null on delete, nullable), `title` (text), `description` (text, nullable — markdown), `priority` (text enum: `none` | `low` | `medium` | `high` | `urgent`, default `none`), `labels` (text, JSON array of strings, default `'[]'`), `created_at` (int), `updated_at` (int).

### kanban_issue_comments

Simple append-only comments on an Issue.

Fields: `id` (text PK), `issue_id` (→ kanban_issues, cascade delete), `content` (text — markdown), `created_at` (int).

### kanban_issue_relations

Records directed relationships between two Issues. Relations are typed: `blocks` means the source Issue is blocking the target Issue; `duplicates` means the source is a duplicate of the target; `relates_to` is a symmetric general relationship. The inverse direction (`is_blocked_by`, `is_duplicated_by`) is derived at query time — when displaying an Issue's relations, retrieve rows where either `source_issue_id` or `target_issue_id` matches the Issue's ID, then infer the label from the direction.

Fields: `id` (text PK), `source_issue_id` (→ kanban_issues, cascade delete), `target_issue_id` (→ kanban_issues, cascade delete), `type` (text enum: `blocks` | `duplicates` | `relates_to`), `created_at` (int).

### Milestone 2 — KanbanService (IPC Layer)

The goal is a fully typed, registered IPC service that the renderer can call to perform every Kanban operation. This milestone has no UI changes; the service is exercised via Electron DevTools console calls.

Create `src/main/services/kanban.ts`. The class `KanbanService` extends `IpcService` with `static readonly groupName = 'kanban'`.

The service must include the following `@IpcMethod()` methods. Each method receives typed arguments, performs a Drizzle ORM query against `getDb()`, and returns plain objects (no class instances). Use `randomUUID()` from `node:crypto` for new IDs. Use `Math.floor(Date.now() / 1000)` for unix epoch timestamps.

**Status methods:**

- `listStatuses(workspaceId: string): KanbanStatus[]` — returns all statuses for the workspace, ordered by `order` ascending.
- `createStatus(input: { workspaceId: string; name: string; color?: string | null }): KanbanStatus` — inserts a new status with `order` set to `(max existing order + 1)` for the workspace (0 if first). Returns the created row.
- `updateStatus(id: string, patch: { name?: string; color?: string | null }): KanbanStatus` — updates `name` and/or `color`, sets `updated_at`... wait, `kanban_statuses` has no `updated_at`. Only update `name` and `color`. Return the updated row.
- `reorderStatuses(workspaceId: string, orderedIds: string[]): void` — receives a full ordered list of status IDs for the workspace and updates each row's `order` field to match the array index. Use a SQLite transaction.
- `deleteStatus(id: string): void` — deletes the status row. Because `status_id` in `kanban_issues` is `SET NULL` on delete (Drizzle's `onDelete: 'set null'`), affected issues will have `status_id = null` automatically.

**Board methods:**

- `listBoards(workspaceId?: string): KanbanBoard[]` — if `workspaceId` is provided, returns boards for that workspace; otherwise returns all boards. Order by `created_at` descending.
- `createBoard(input: { workspaceId: string; name: string; filterConfig?: string | null }): KanbanBoard` — inserts a new board and returns it.
- `updateBoard(id: string, patch: { name?: string; filterConfig?: string | null }): KanbanBoard` — updates the board and sets `updated_at`. Returns the updated row.
- `deleteBoard(id: string): void` — deletes the board (no foreign key dependencies on the board from issues; boards are views, not containers).

**Milestone methods:**

- `listMilestones(workspaceId: string): KanbanMilestone[]` — all milestones for workspace, order by `created_at` descending.
- `createMilestone(input: { workspaceId: string; title: string; description?: string | null; dueDate?: number | null }): KanbanMilestone`
- `updateMilestone(id: string, patch: { title?: string; description?: string | null; dueDate?: number | null; status?: 'open' | 'closed' }): KanbanMilestone`
- `deleteMilestone(id: string): void`

**Issue methods:**

- `listIssues(params: { workspaceId: string; milestoneId?: string | null; parentIssueId?: string | null; priority?: string | null; labels?: string[] | null; statusId?: string | null }): KanbanIssue[]` — apply all provided filters. `labels` filter means "issue's labels JSON contains ALL specified label strings" (perform a `LIKE` check per label). Order by `created_at` descending.
- `getIssue(id: string): KanbanIssue | undefined`
- `createIssue(input: { workspaceId: string; title: string; description?: string | null; priority?: string; labels?: string[]; milestoneId?: string | null; parentIssueId?: string | null; statusId?: string | null }): KanbanIssue`
- `updateIssue(id: string, patch: Partial<{ title: string; description: string | null; priority: string; labels: string[]; milestoneId: string | null; parentIssueId: string | null; statusId: string | null }>): KanbanIssue` — updates fields present in `patch`, sets `updated_at`.
- `moveIssue(id: string, statusId: string | null): KanbanIssue` — convenience method to change only `status_id`; equivalent to `updateIssue(id, { statusId })` but semantically distinct for clarity.
- `deleteIssue(id: string): void`

**Comment methods:**

- `listComments(issueId: string): KanbanIssueComment[]` — order by `created_at` ascending.
- `addComment(input: { issueId: string; content: string }): KanbanIssueComment`
- `deleteComment(id: string): void`

**Relation methods:**

- `listRelations(issueId: string): KanbanIssueRelation[]` — returns all relation rows where `source_issue_id = issueId` OR `target_issue_id = issueId`, ordered by `created_at` ascending.
- `addRelation(input: { sourceIssueId: string; targetIssueId: string; type: 'blocks' | 'duplicates' | 'relates_to' }): KanbanIssueRelation`
- `deleteRelation(id: string): void`

After creating the service, open `src/main/index.ts` and:

1. Add `import { KanbanService } from './services/kanban'` alongside the other service imports.
2. Add `KanbanService` to the array passed to `createServices([...])`.

Open `src/main/ipc-types.ts` and:

### Milestone 6 — Issue Side Panel

The goal is a fully functional Issue detail panel that allows editing all Issue fields and managing comments and sub-issues.

**`src/renderer/src/features/kanban/issue-panel.tsx`:**

3. **Description**: a `<textarea>` for markdown description. Show a preview toggle button (renders markdown via a lightweight renderer — use `marked` if it is already installed; check `package.json`). Save on blur.

4. **Labels**: a tag input where pressing Enter or comma adds a label chip. Clicking an existing chip removes it. Saves on blur.

5. **Sub-issues**: a titled section listing `<IssueCard />` items where `parent_issue_id = this issue's id`. A "Add sub-issue" button opens an inline form (title only) that calls `createIssue({ parentIssueId: currentId, workspaceId, ... })`. Sub-issues appear as compact cards (title + priority badge only) inside the panel and also as full cards in their respective status columns on the board (their `status_id` works independently of the parent).

6. **Relations**: a titled section showing four groups derived from `listRelations(issueId)`: "Blocks", "Blocked by", "Duplicates", and "Relates to". Each group lists the related Issue's title as a clickable link that selects that Issue in the panel. An "Add relation" button opens a small inline form: a type selector (dropdown of the four relation types) and an Issue search input (searches by title via `listIssues({ workspaceId })`). Submitting calls `addRelation`. Each existing relation entry has a remove button that calls `deleteRelation`. When displaying the relationship labels, derive them from the stored `type` and direction: a row where `source_issue_id = this issue` and `type = 'blocks'` shows under "Blocks"; the same row accessed from the target issue shows under "Blocked by". A row with `type = 'relates_to'` shows under "Relates to" regardless of direction.

7. **Comments**: a reverse-chronological (oldest first in display, newest at bottom) list of comments. Each comment shows the `content` rendered as markdown and a delete button. A textarea + submit button at the bottom adds a new comment via `addComment`.

Acceptance: open an Issue panel, add a comment, create a sub-issue, mark another issue as blocking the current one, change the status, and verify all changes persist after restarting the app.

## Idempotence and Recovery

Running `pnpm drizzle-kit generate` multiple times is safe as long as the schema file hasn't changed between runs. If the migration file already exists with the correct content, re-running generate is a no-op.

If a migration was applied and then the schema regresses (e.g. a git revert), the safest recovery is to delete the local `cradle.db` file (at `~/Library/Application Support/Cradle/cradle.db` on macOS) and restart the app to apply migrations from scratch. Development data is lost but the schema recovers cleanly.

All IPC mutations are synchronous SQLite writes wrapped in Drizzle's transaction helpers where atomicity matters (e.g. `reorderStatuses`). There is no async queue or background worker to worry about.

## Decision Log

- 2026-04-23: `workspace === project` — no new project table. The existing `workspaces` table is the top-level container for all Kanban entities. Rationale: Cradle already uses workspaces as local-repo units; introducing a separate project concept would duplicate the workspace concept without adding meaningful structure.
- 2026-04-23: Status-filter model (Method A) — Issues have a `statusId` field; columns are status enum items scoped to the workspace, not per-board. Rationale: consistent with GitHub Projects V2 model; different boards for the same workspace share the same status vocabulary and operate as filtered views rather than independent containers.
- 2026-04-23: `filterConfig` is persisted in DB — boards are named, reusable views whose filter state is durable.
- 2026-04-23: No manual ordering of Issues within a column — issues are sorted by `created_at` descending by default. Rationale: removes fractional-indexing complexity; user preference expressed via filter and drag-to-status-change rather than manual card reordering.
- 2026-04-23: Use `@dnd-kit/core` + `@dnd-kit/sortable` for drag-and-drop — replaces the initial consideration of native HTML5 drag-and-drop. Rationale: @dnd-kit provides accessible, performant, React-idiomatic DnD with built-in sortable support needed for both card-between-columns movement and status reordering in the management UI. It is the de-facto standard in the modern React ecosystem (used by Vercel, Radix, etc.).
- 2026-04-23: Cross-workspace boards deferred — `kanban_boards.workspaceId` is NOT nullable for the initial implementation. Cross-workspace board support is a V2 concern.
- 2026-04-23: No Agent integration in this plan — Kanban is a standalone task-tracking feature. Future integration (card triggering an agent session, session result written back to card) will be a separate ExecPlan.
- 2026-04-23: Self-referential FK for sub-issues handled at application layer — Drizzle's schema builder does not support self-referential `.references()` declarations. The `parent_issue_id` column is a plain `text` field. On issue deletion, the KanbanService must explicitly set `parent_issue_id = null` on child issues before deleting the parent (to avoid dangling references).
- 2026-04-23: Issue relations added to schema (6th table: `kanban_issue_relations`) — supports `blocks`, `duplicates`, and `relates_to` relation types. Inverse relations (`is_blocked_by`, `is_duplicated_by`) are UI-layer derivations, not stored as separate rows. Querying is bidirectional: `source_issue_id = X OR target_issue_id = X`.
- 2026-04-23: GitHub Projects model confirmed over Linear model — workspace-wide status vocabulary is the correct choice for Cradle's architecture. Per-workspace-per-project status differentiation would require a separate project entity above workspace, which contradicts the established `workspace === project` constraint. All boards for a workspace share the same status list; this is made clear in the UI via the "Manage statuses" label (not "Manage columns").

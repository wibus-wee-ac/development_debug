## Purpose / Big Picture

Cradle needs a simple way to tell whether a chat session was created manually or by a Cradle-owned workflow such as automation, Cradle Review, or Cradle Issue delegation. After this change, every chat session has one coarse `origin` string. Users and agents can list or search sessions by this origin, for example to find sessions generated by Cradle Review without needing to inspect diff-review tables first.

The visible behavior is intentionally small. Existing sessions and ordinary user-created sessions show `origin: "manual"`. Sessions created by automation show `origin: "automation"`. Sessions created from Cradle Review and Cradle Diffs workflows show `origin: "cradle-review"`. Sessions created from issue delegation show `origin: "cradle-issue"`. The session list API and thread search API can filter by `origin`.

## Decision Log

- Decision: Store a single `origin: string` on `sessions`, not a separate annotation/provenance table.
  Rationale: The immediate product need is coarse retrieval and grouping, not detailed lifecycle modeling. Detailed semantics such as guide vs agent fix remain owned by their source modules through existing `sessionId` and `runId` links. A single string is enough and avoids over-design.
  Date/Author: 2026-06-20 / Codex

- Decision: Use coarse values only: `manual`, `automation`, `cradle-review`, and `cradle-issue`.
  Rationale: The user explicitly rejected owner-qualified or highly granular values. `cradle-review` covers Cradle Review / Cradle Diffs generated sessions, including guides and agent fixes. If Commit Plan later becomes Chat Runtime-backed, it should also use `cradle-review`.
  Date/Author: 2026-06-20 / Codex

- Decision: Keep `origin` as a plain string in public APIs instead of a TypeScript enum or database enum.
  Rationale: The repository instruction says not to casually invent new types or projections. A string keeps the interface simple and allows future owners to add coarse origins without a schema-level enum migration.
  Date/Author: 2026-06-20 / Codex

- Decision: Do not make `origin` editable through the generic session update route in the first slice.
  Rationale: Origin describes how a session was created. Allowing generic edits would blur ownership and make search results less trustworthy. Callers set it at creation time; existing sessions default to `manual`.
  Date/Author: 2026-06-20 / Codex

- Decision: Preserve `origin` in existing frontend normalizers instead of adding a frontend-only projection type.
  Rationale: The generated API types already describe `origin` as part of the response. The existing Zod normalizers are the correct local boundary, and adding the field there keeps the API shape intact without inventing another projection.
  Date/Author: 2026-06-20 / Codex

## Context and Orientation

The repository root is `/Users/wibus/dev/Cradle`. The server is an Elysia TypeScript application in `apps/server`. The database schema is owned by `packages/db` and uses Drizzle. Drizzle is the type-safe ORM used in this repository; schema changes should be made in `packages/db/src/schema/*.ts` and materialized as migrations under `packages/db/drizzle/`.

The chat session persistence model lives in `packages/db/src/schema/chat.ts`. The `sessions` table is the product-level session record. It is distinct from Chat Runtime runs and provider bindings. Chat Runtime owns run lifecycle facts such as `backend_runs` and `session_events`, but the session module owns session metadata such as title, archive status, provider target, model preference, and now `origin`.

The session API lives in `apps/server/src/modules/session/`. `model.ts` defines the HTTP request and response schemas. `service.ts` implements list, get, create, update, archive, delete, messages, and markdown export. `index.ts` wires those functions to Elysia routes under `/sessions`.

Several server modules create sessions on behalf of workflows. `apps/server/src/modules/automation/service.ts` creates sessions for automation runs. `apps/server/src/modules/issue-agent/service.ts` creates sessions for issue delegation. `apps/server/src/modules/diff-review/service.ts` creates sessions for Cradle Diffs Guide and Agent Fix flows. These modules should set `origin` at session creation. Manual UI/API-created sessions should not need to pass anything and should receive `manual`.

Thread search lives in `apps/server/src/modules/search/thread-search.engine.ts` and is exposed by `apps/server/src/modules/search/index.ts`. It searches session titles and completed message content. It has an FTS path when the SQLite `messages_fts` virtual table exists and a legacy scan fallback when FTS is unavailable. Both paths must apply the same `origin` filter.

Generated web API clients live in `apps/web/src/api-gen/` and should be regenerated by `pnpm generate:web` after changing OpenAPI-visible server schemas. Generated CLI commands live in `packages/cli/src/commands/generated/` and should be regenerated by `pnpm gen:cli` after changing route schemas or `x-cradle-cli` surfaces.

## Plan of Work

First, add `origin` to the database schema. In `packages/db/src/schema/chat.ts`, add `origin: text('origin').notNull().default('manual')` to the `sessions` table near other session-owned metadata. Add an index, preferably `byOrigin: index('sessions_origin_idx').on(table.origin)`, so list and search filters can stay cheap. Generate the next Drizzle migration with `pnpm --filter @cradle/db generate`. The current latest migration observed before this plan is `0005_right_gauntlet.sql`, so the generated migration should be the next `0006_*.sql`. If Drizzle chooses a different generated filename, keep its generated name.

Second, expose the field through the session module. In `apps/server/src/modules/session/model.ts`, add `origin: t.String()` to `SessionModel.session`. Add `origin: t.Optional(t.String({ minLength: 1 }))` to `createBody` and `listQuery`. In `apps/server/src/modules/session/service.ts`, extend `SessionCreateInputSchema` with `origin: z.string().trim().min(1).default('manual')`, add `origin?: string` to the exported `create` input type, and insert `origin: parsed.origin` into the `sessions` insert. In `list`, add an `eq(sessions.origin, input.origin)` predicate when an origin filter is supplied. Do not add origin to `updateBody` or `Session.update`.

Third, set origins at workflow-owned creation sites. In `apps/server/src/modules/automation/service.ts`, pass `origin: 'automation'` to `Session.create`. In `apps/server/src/modules/issue-agent/service.ts`, pass `origin: 'cradle-issue'`. In `apps/server/src/modules/diff-review/service.ts`, pass `origin: 'cradle-review'` for guide generation and agent-fix run creation. Do not set `origin` for generic user-created sessions; they will default to `manual`.

Fourth, update thread search. In `apps/server/src/modules/search/thread-search.engine.ts`, add `origin?: string` to `ThreadSearchParams` and its Zod schema. Add `origin: string` to `ThreadSearchHit` so search results can show why a session appears in an origin-filtered result. In the FTS path, when reading each candidate session, reject it if `params.origin` is set and `session.origin !== params.origin`. In the legacy path, include the origin predicate in the initial session query, using Drizzle `and` with the workspace predicate when both filters are present. Update `apps/server/src/modules/search/model.ts` so the HTTP query accepts optional `origin` and each hit returns `origin`.

Fifth, update docs and generated clients. In `apps/server/src/modules/session/README.md`, add one paragraph explaining that `origin` is session-owned coarse source metadata and that source modules retain detailed lifecycle ownership. Regenerate web API and CLI code using the commands in Concrete Steps. Do not manually edit files under `apps/web/src/api-gen/` or `packages/cli/src/commands/generated/`; change server schemas and rerun the generators.

Sixth, add focused tests. In `apps/server/tests/session.test.ts`, add assertions that creating a session without `origin` returns `manual`, creating a session with `origin: 'automation'` persists that string, and `Session.list({ origin: 'automation' })` or the HTTP list endpoint returns only matching sessions. In `apps/server/tests/search.test.ts`, add two sessions with the same searchable text but different origins and assert `searchThreads({ query: '...', origin: 'cradle-review' })` returns only the Cradle Review session and includes `origin: 'cradle-review'`. Add workflow creation assertions only where the existing tests already exercise that creation path; do not build a large new integration test just to inspect a field.

## Validation and Acceptance

The main acceptance behavior is API-visible and testable without launching the full desktop app.

After implementation, a session created through the normal `/sessions` API without an origin has `origin: "manual"` in the response. A session created with body `origin: "automation"` has that exact string in the response and in later `GET /sessions/:id`. `GET /sessions?origin=automation` returns automation-origin sessions and excludes manual sessions. `GET /search/threads?query=<shared text>&origin=cradle-review` returns only matching sessions whose origin is `cradle-review`, and each hit includes `origin: "cradle-review"`.

Server tests should cover these cases directly. Type checks prove the generated web and CLI clients are consistent with the server OpenAPI schema. No browser-based frontend test is required for this backend/API slice.

## Idempotence and Recovery

The code edits are additive and safe to retry. Running `pnpm --filter @cradle/db generate`, `pnpm generate:web`, and `pnpm gen:cli` multiple times should be deterministic once the schema is stable. If Drizzle generates an unwanted duplicate migration because the first generated file was not kept, remove only the duplicate generated migration you just created and rerun generation from the current schema; do not revert unrelated user changes.

If focused tests fail because generated client files are stale, rerun `pnpm generate:web` and `pnpm gen:cli` before changing source behavior. If search tests fail only on the FTS path, verify that both `searchFts` and `searchLegacy` apply the same origin predicate. If a workflow-origin test is too expensive or brittle, prefer a focused service-level test around the relevant `Session.create` call rather than broad UI testing.

This change adds a non-null database column with a default, so existing rows should become readable as `manual`. The migration should not delete or rewrite messages, runs, or provider bindings.
